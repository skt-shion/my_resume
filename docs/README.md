## 職務経歴詳細

### データ基盤MCPサーバー開発・リリース（N株式会社: 2026/6 ~ 2026/9）

【担当領域 / 役割】

本MCPサーバーの企画・アーキテクチャ設計・開発・インフラ構築・リリース後の運用改善までを一貫して対応。

- **アーキテクチャ設計:** フルスクラッチではなく、AWS Labsが公開するRedshift向け公式MCPサーバー（OSS）をフォーク。自社のネットワーク・認証・運用要件に合わせてカスタマイズする方針を採用。
- **バックエンド開発:** FastMCPを用いたMCPツール（テーブル探索・カラム情報取得・SQL実行）の実装、Redshift Data APIとの連携、SQL実行時のREAD ONLYトランザクションラップによる安全性担保の実装。
- **認証基盤の統合:** Google OAuth 2.0によるクライアント認証の導入、MCP仕様が要求するDynamic Client Registration（DCR）と、DCR非対応のGoogle OAuthとの間のプロトコル変換（OAuthプロキシ）の実装。
- **インフラ構築:** TerraformによるAWSリソースのIaC化。
- **リリース後の運用改善:** コンテナ再起動時の認証継続性確保、、IAM権限の最小化、利用部門からのネットワーク要件への対応、監視の追加など、運用を通じて明らかになった課題への継続的な対応。

【課題】

- 社内のデータ基盤（Redshift）への問い合わせ手段がBIツール経由で発行するSQL依存になっており、データ分析業務の属人化・ハードルの高さが顕在化していた。
- テーブル構成やカラムの意味を知らない利用者が誤ったクエリを書くリスクがあった。
- 誰が・いつ・どのようなクエリを実行したかを追跡する手段がなく、安全な運用のための監査や、障害発生時の影響範囲特定が困難だった。

【工夫した点】

段階的リリース、OSSの再利用による開発効率化、構造的な安全性担保、認証プロトコルの橋渡し、ステートレスな実行基盤への適応を軸に様々な工夫を凝らした。

- **小規模PoC起点の段階的リリース:** 新規Terraformモジュールをゼロから設計する前に、社内の既存モジュールを間借りして最小構成の実験環境を素早く立ち上げ、無認証のチーム内試験運用から着手。そこから認証・IAM権限などのセキュリティ対策を施して本番リリースへ移行し、リリース後も実運用で見えた課題に都度対応する形で、機能・運用改善を継続的に積み重ねる進め方を取った。最初から完成形を設計せず、小さく始めて利用実態に応じて継ぎ足していくことで、過剰な初期設計コストを削減し、現場への迅速な価値提供に重きを置いた。
- **公式OSSをベースに自社要件へ絞り込み:** フルスクラッチ開発を避け、AWS公式が提供するRedshift向けMCPサーバーを土台に採用。自社では使わないRedshift Serverless対応・複数クラスター横断検索機能は削除してスコープを縮小し、自社特有の認証・運用要件の実装に開発リソースを集中させた。
- **構造的な安全性担保:** SQL文字列のパターンマッチだけに頼らず、「READ ONLYトランザクションでラップして実行する」ことを主軸とした構造的なガードレールにより、意図しない書き込みを仕組みで防止した。
- **認証プロトコルの橋渡し:** MCPクライアントが前提とするDynamic Client Registration（DCR）と、DCRに非対応なID基盤（Google Workspace）との間を、OAuthプロキシ層を実装することで対処した。
- **ステートレス実行基盤への適応:** コンテナが再起動するたびに認証クライアントの登録状態が失われ、利用者が再ログインを強いられるという問題に対し、登録情報を透過的に復元する仕組みを独自実装して解消した。
- **利用者追跡の仕組み化:** 複数利用者が同一のDB接続セッションを共有する構成上、実行者を特定する手段がなかったため、SQLクエリへのコメント埋め込みによる利用者追跡機能を実装した。

【成果】

- 非エンジニア含む社内ユーザーが、AIエージェント経由で自然言語を介して、データ分析を行えるセルフサービス型の分析環境を実現。
- 全クエリをREAD ONLYトランザクションで実行し、かつ実行者をログから追跡可能にしたことで、安全かつ監査可能なデータ分析環境を確立。
- 利用実績として、公開初週でDAU約20~30、1ヶ月後には約40~50まで推移し、組織のデータ活用文化を促進した。

【後悔していること】

- **本番リリースまでの期間を取りすぎた:** 1-2週程度で早期リリースし利用者のフィードバックを得ながら継続的に改善を続けていく方が価値提供までの速度を向上できた。
- **ドキュメント整備の後回し:** 機能追加や運用対応を優先した結果、利用者向けドキュメント、開発者向けドキュメントの整備が遅れ、後から振り返って全体像を把握するコストが高くなってしまった。

### データカタログのリニューアル -（N株式会社: 2026/4 ~ 2026/8、以降運用保守）

【担当領域 / 役割】

日常的にデータ分析を業務に取り入れている社内のデータ利用者（アナリスト・マーケター等）向けに提供していた簡易版データカタログを、将来的な全社的データ活用の拡大を見据えてリニューアルするプロジェクトで、要件定義・製品選定・アーキテクチャ設計・インフラ構築・リリース後の運用改善までを一貫して担当。

- **要件定義・製品選定:** 既存カタログの課題整理、複数の OSS メタデータカタログ製品の比較評価、採用製品の選定。
- **指標・ロードマップ設計:** KPI（ドメイン設定率、テーブル・カラム説明付与率）の定義、段階的なリリースロードマップの設計。
- **ガバナンス設計:** データメッシュに基づくドメイン単位の情報設計、SSO 連携、問い合わせ導線のためのグループ設計。
- **アーキテクチャ設計:** 選定した OSS 製品と既存データウェアハウス（Amazon Redshift）・BI/dbt 環境との接続構成設計。
- **インフラ構築:** Terraform / Kustomize / ArgoCD による IaC・GitOps デプロイ基盤の構築。
- **検索基盤の最適化:** 日本語検索精度を確保するための形態素解析エンジンの選定・チューニング。
- **メタデータ取り込み基盤の構築:** Redshift, dbtメタデータ連携ワークフロー（Prefect）の構築。
- **OSS の不具合対応:** 採用製品に存在したバージョン固有の不具合の調査・回避策実装。
- **リリース後の運用改善:** 認証鍵管理の自動化、IAM 権限最小化、CI/CD 安定化、運用ドキュメント整備。

【課題】

- 既存のデータカタログが dbtの標準ドキュメントと手動管理スプレッドシートにとどまっており、UI の使いやすさ・全文検索の精度・テーブル/カラムレベルのリネージ可視化・データ品質/鮮度の可視化のいずれも不十分だった。
- メタデータの維持・拡充がデータエンジニアに依存する構造になっており、非データアナリスト（営業・企画チーム等）やデータ分析AIエージェントが自らデータ資産を探し出して扱える状態には程遠かった。
- データ資産の意味や品質に関する問い合わせ先が明確でなく、ドメイン知識を持つ担当者とデータ基盤運用担当者のどちらに確認すべきか利用者側で判断できなかった。
- 日本語のテーブル名・カラム説明を正確に検索できる基盤が必要だったが、既存のカタログでは検索精度のカスタマイズが困難だった。

【工夫した点】

製品選定の客観性確保、データメッシュ型のガバナンス設計、段階的なメタデータ拡充、日本語検索の精度と運用コストの両立、セキュアな認証を軸に様々な工夫を凝らした。

- **複数軸評価による製品選定:** UI/UX、API/SDK/MCP 対応、運用コスト、SaaS対応、生成AI対応、日本語対応、データリネージ・全文検索・タグ付け・データ品質可視化等の機能面、拡張性、セキュリティ、チーム文化との親和性などの複数の評価軸で比較レポートを作成し、「データエンジニアを介さずにメタデータが時系列で成長し続ける」という思想を持つ製品を選定。OSS版だけで主要機能がほぼ揃っており社内の稟議手続きを経ずに迅速に導入開始できる点、将来的にマネージドSaaS版への移行パスが用意されている点、日本語検索精度のカスタマイズや将来のセマンティック検索対応まで見込める点を重視した。
- **データメッシュ型のガバナンス設計:** データ資産をビジネス領域単位で分類し、ドメイン担当者グループ・データ基盤担当者グループ・一般利用者グループの3層でグループ設計。データ資産に両グループを紐づけることで、データの意味に関する問い合わせはドメイン担当者へ、品質・更新状況に関する問い合わせはデータ基盤担当者へ自然に誘導される仕組みと文化の土台を作った。
- **段階的なメタデータ拡充戦略:** 一度にすべての情報を揃えようとせず、まず既存カタログと同等量のメタデータ（テーブル・カラム説明、担当チーム、更新頻度等）を投入して早期リリースすることを優先。リリース後にドメイン定義、dbtのテスト結果・鮮度チェック結果の可視化、既存BIダッシュボード情報の取り込みによる逆引き探索などを継続的に拡張するロードマップとした。メタデータの拡充・定着は一朝一夕で完了するものではなく、中長期的な視点で利用者への普及活動も並行して必要という前提に立っての計画。
- **日本語検索の段階的な最適化:** まず標準でビルトインされている形態素解析エンジンを採用して早期にリリースし、将来的な高度化（別の形態素解析エンジンへの移行）を見据えてプラグインの事前導入のみ済ませておき、リリース速度と将来の拡張性を両立する進め方を取った。
- **最小権限でのクロスアカウント認証設計:** 認証情報を保持せず、IAM ロールの引き受け（AssumeRole）を多段に組み合わせることで、必要な範囲でのみ一時クレデンシャルを払い出す設計とした。
- **レガシー化防止のための初期CI/CD整備:** 初期構築サイクルの高速化、及びリリース後の機能追加・不具合対応に備え、IaC・GitOpsのデプロイ基盤を初期段階で整備し、リリース後も継続的に改善できる体制を構築した。

### PCオンラインゲーム・モバイルゲームのサーバー管理・運用（株式会社N: 2017/04 ~ 2020/03）

【担当領域 / 役割】

DAU約8000のオンラインゲームサービスを支えるインフラ基盤の運用・保守業務を担当。担当タイトル：イニシャルAS, TS, GS

- **サーバー運用・管理:** 安定的な運用を第一とし、サービス障害を未然に防ぐ日々のモニタリングおよびサーバーメンテナンスを実施。
- **業務自動化・改善:** TSにおいて、パッチ適用ツールの作成や定型業務の自動化を行い、既存運用フローの業務改善を実施。
- **リソース最適化:** ASのAWS移行後、継続的なリソース管理と構成の最適化を実施。
- **OSマイグレーション:** CentOS 6のEOLに伴う、OSマイグレーション。
- **コンテナ環境におけるモニタリング基盤刷新:** ZabbixからPrometheusへの移行。
- **ログ収集・集約基盤構築:** 各サーバーのローカルに点在しているゲームサーバーログを一か所に集約。
- **役割:** メンバー（サーバー運用・管理担当）。

【課題】

- 24時間365日持続的にサービスを提供し続けなければならず、サービス停止時間が売上に直結する点
- 手動による定型業務が多く、ヒューマンエラーのリスクと工数負荷があった点。

【工夫した点】

- オペレーションミスによるシステム障害に繋がらないよう、緊急の障害対応などの明確な理由がない限りは稼働中の本番システムへのリモート接続を行わないようにした。リモート接続に気づくことができるように、いつ、誰が、どのサーバーに、どこから接続したのかをメール通知で気づける仕組みを構築した。
- システム構成・設計・パラメータ資料や運用手順書等のドキュメント類を整備し、特に「なぜこうしたのか？」が分かるように背景や意図を明記することを重視した。
- サーバー上での作業は極力rootユーザーで行わない、変更を伴う場合は必ずバックアップを取得する、毎回の定期メンテナンス前には必ず手順書とスクリプトを用意することを徹底した。

【成果】

- システムモニタリングと安全なメンテナンス作業の徹底による24時間365日安定運用に貢献。

### PCオンラインゲームサービスのAWS基盤移行プロジェクト（株式会社N: 2018/07 ~ 2019/04）

【担当領域 / 役割】

オンプレミス環境で稼働していたタイトル「イニシャルAS」および「イニシャルTS」のインフラ基盤をAWS環境へ移行するプロジェクト。

- **要件定義・設計:** オンプレ環境の構成把握、AWS環境におけるサーバー・サービス構成の考案。
- **コスト試算:** インスタンスタイプ、ボリューム設計、必要リソースを見積もり、月単位のコスト概算を算出。
- **構築・検証:** AWS環境構築、各種サービス連携設定、サーバーアプリケーションの起動・内部動作確認。
- **進捗管理:** 全体的なタスク・スケジュール管理の遂行。

【課題】

- オンプレミス特有の複雑な依存関係や構成を正確に把握し、AWS環境で再現・最適化する必要があった点。
- 海外デベロッパー、社内開発チーム、運用チームなど多岐にわたるステークホルダーのタスクと工数を見積もり、サービス停止を最小限に抑えた移行スケジュールを完遂しなければならなかった点。

【工夫した点】

- 移行初期段階でオンプレミス環境のシステム・ネットワーク全体構成を詳細に把握することに注力し、移行における課題点の早期洗い出し。これにより設計フェーズが盤石になり、リスクを分散させる段階的な移行計画を策定することができた。
- 変更箇所は少ないほどリスクが下がる。移行リスクを最小限に抑えるため、既存の環境・構成を可能な限り同等レベルで再現するよう努めた。
- 同等の環境・構成にプラスアルファで、マネージドサービスで提供される機能を活用して可用性と運用負荷を緩和できるような設計を心がけた。
- 関係各所調整と移行リスクを踏まえたタスク・スケジュール管理を行うことで大きなトラブルもなく、ある程度の余裕をもって移行を完遂することができた。
- AWS移行後のランニングコスト増大を防ぐため、設計段階から消費リソースに見合う適切なインスタンスタイプ、ストレージを選定し、クラウドコスト最適化に努めた。
- 移行日直前に直属の上司によるレビューを実施してもらい、安全な移行に係る見落とし点やリスク要因の洗い出しが功を奏した。（DNSレコードのTTL問題）

【成果】

- 2タイトルのAWS移行を大きなトラブルなく完遂。
- 移行後の継続的な構成最適化により、オンプレミス時代と比較して50%以上のランニングコスト削減を実現した。
- 移行作業だけでなく、管理業務（タスク・スケジュール管理）を経験したことで、プロジェクト遂行能力を大きく向上させた。

- 社内: ゲームタイトル運用部隊、Web開発部隊、サポート部隊
